## 背景

变更动机见 `proposal.md`，用户可观察行为见四份增量规范。

nanobot 当前通过 `MessageBus` 接收渠道消息，通过 `nanobot.command` 路由 Slash Command，通过自动发现的工具注册机制运行 Agent 工具，并在 `OutboundMessage.event` 上承载类型化运行时语义。渠道入口已经能够校验和保存附件，`nanobot.utils.document` 也为 PDF、DOCX、XLSX、PPTX 和文本格式提供了有界文本提取。但项目目前没有持久化文档库、Embedding 运行时、词法/向量索引或 RAG 任务协调器。

本设计必须保持 Python 3.11+、asyncio 响应性、渠道可选依赖、严格类型检查和 nanobot 的轻量基础安装。同时还必须处理本地 CPU 推理延迟、来自多个聊天平台的不可信文件、进程重启、平台差异，以及每个主体接近 1 GiB 的私人语料。

## 目标与非目标

**目标：**

- 在边界清晰的小型接口后引入可选的 `nanobot/rag/` 子系统，避免把检索逻辑散落到 AgentLoop 和各渠道实现中。
- 让授权校验和存储隔离各自独立生效。
- 保持入库持久化、异步执行，并让交互式检索拥有更高调度优先级。
- 在解析、切片、检索和引用的全链路保留来源结构。
- 使用统一的本地推理 API，并为硬件加速设置正确性门禁。
- 通过现有事件架构发布 RAG 进度。
- 使所有持久化状态转换都可恢复、可测试、可观测，同时不记录知识正文。

**非目标：**

- 替换现有附件处理或会话记忆。
- 创建远程 RAG 服务或独立向量数据库守护进程。
- 在第一版中把私人知识库扩展成共享 ACL 系统。
- 根据硬件自动切换到更大的 Embedding 模型。
- 在真实评测结果出现前实现 OCR 或高级检索策略。

## 技术决策

### 1. 新增边界清晰的可选 RAG 子系统

在 `nanobot/rag/` 下按职责拆分类型与模型、配置、身份与策略、存储、解析、切片、词法分析、本地推理、硬件 Profile、入库任务、检索、进度和 Manager 门面。命令与工具只能通过 `RagManager` 使用应用级 RAG 能力。

只有在 RAG 启用且依赖校验通过时，网关才构造 Manager。AgentLoop 获取一个可选的知识检索工具，该工具绑定服务端创建的请求上下文。渠道 Adapter 只提供能力事实、附件和路由元数据，不实现 RAG 业务规则。

未采用的方案：

- 不把 RAG 逻辑直接写入 `AgentLoop`，因为入库生命周期、存储和模型资源属于独立关注点，这样会继续扩大核心组件。
- 不建设外部 RAG 服务，因为它违背本地优先隐私目标，也提高轻量框架的部署复杂度。

### 2. 把主体和会话范围作为服务端可信上下文

扩展渠道能力契约，使 Adapter 能报告消息是否具有稳定且已认证的发送者 ID，以及会话类型是私聊、群聊/公开或未知。RAG 策略层只接受“稳定身份 + 私聊”，其他情况失败即关闭。

主体的规范字节由 `channel`、NUL 分隔符和 `sender_id` 组成，经带领域分隔的 SHA-256 得到存储目录名。`chat_id` 和 session key 继续只负责路由和会话，不作为身份。知识库工具 Schema 不包含主体字段；`AgentLoop` 在验证当前消息后注入不可变的 `RagRequestContext`。

每个主体使用物理独立存储，作为应用层策略的第二道防线。未来共享知识库可以增加新的 Store 类型，但不能削弱私人 Store 的隔离不变量。

未采用全局 Store 加 `principal_id` 过滤，因为一次过滤遗漏、ANN 后过滤行为或未来查询改动都可能直接造成跨用户泄漏。

### 3. 每个主体使用 SQLite 与 USearch 版本化代次

每个主体目录包含一份 SQLite 数据库、托管原始文件、临时任务目录和不可变的版本化 USearch HNSW 文件。SQLite 是文档、Chunk、FTS 行、任务、配额预占和活动向量代次的持久化事实来源。

核心表：

- `documents`：文档 ID、显示名称、摘要、MIME、原始字节、生命周期状态、时间戳、错误码和活动代次成员关系。
- `chunks`：整数向量键、文档 ID、顺序、原文、Token 数、位置 JSON 和 Embedding Profile ID。
- `chunks_fts`：关联 `chunks` 的规范化词法文本。
- `jobs`：操作、持久状态与阶段、尝试次数、来源路由元数据、安全错误和时间戳。
- `quota_reservations`：批次/任务归属、字节数量和预占状态。
- `store_manifest`：Schema 版本、活动向量代次和 Embedding Profile 签名。

索引更新写入 `vectors/generation-<id>.usearch` 和匹配的暂存数据库状态。系统验证数量、键、维度和 Profile 后，通过短事务激活新代次。查询固定一个代次，垃圾回收只在读取者释放旧代次后删除文件。这种方式不依赖替换已打开的内存映射文件，在 Windows 和 POSIX 上都安全。

选择 USearch 是因为它提供嵌入式 HNSW、持久化、内存映射读取、量化存储和跨平台 Python Binding。LanceDB 虽然自带 Hybrid 检索，但会引入更大的存储栈，并重复本功能必须自行控制的生命周期和 FTS 策略。SQLite 向量扩展也被评估过，但面对较大的用户 Chunk 数量，第一版需要更成熟的 ANN 行为。

### 4. 配额以事务方式预占，内容去重仅限当前主体

Manager 校验完整 `/rag add` 批次，计算待加入的原始字节，并在同一个 SQLite Immediate Transaction 中创建任务与配额预占。事务按“已提交 + 已预占”计算用量并全收或全拒。默认上限为 1 GiB；派生数据不计入用户显示额度，但受全局磁盘策略保护。

复制原始文件到任务目录时流式计算 SHA-256。同一主体下的重复内容指向既有文档，不再提交第二份原始文件或配额。文件名相同但内容不同则获得新 ID。第一版不做跨主体物理去重，避免删除和隔离依赖共享 Blob 引用计数。

删除先提交“不可检索”状态，再清理 Chunk 和 FTS 并发布不含该文档的新向量代次。原始文件清理完成后才释放配额。失败时文档保持不可见并可安全重试。

### 5. 入库使用持久化状态机

持久阶段为 `queued`、`parsing`、`chunking`、`embedding`、`indexing`，终态为 `ready` 或 `failed`。每次转换记录时间戳、尝试次数和安全错误类别。网关启动协调器，恢复未终止任务并运行有界 Worker。

各阶段只写任务工作目录或新索引代次。重启恢复时，系统复用经过验证的阶段产物，或者删除不安全产物后重跑该阶段。任何内容在就绪发布事务前都不可检索。临时基础设施错误最多退避重试两次；校验失败、不安全文件、不支持格式、配额不足和空文本属于永久错误。

默认同时只有一个后台 Embedding 任务。协调器分别限制解析进程、Embedding、Reranker 和索引发布的并发。交互请求在有界入库批次之间进入更高优先级的推理队列。

不采用同步 `/rag add`，因为纯 CPU 处理大文档会超过渠道请求时限，也会让用户误以为机器人卡死。

### 6. 把文档提取扩展为结构化、失败即关闭的结果

在现有提取器后增加结构化结果，包含文本块、来源位置、检测格式、截断/安全状态和安全错误码。现有当前轮次调用者通过兼容 Adapter 仍能得到原来的字符串行为。

RAG 解析在 Worker Process 中运行，受墙钟超时，以及文件、压缩包、成员、页数、内容流、字符、表格和行数限制。达到限制必须明确报告，不能把现有的人类可读截断后缀误认为全文已入库。

位置生成器保留 PDF 页码、文档标题路径、幻灯片编号、工作表与行范围或文本行号。OOXML 公式只读取已存储或显示值，不执行宏或文档代码。图片占位符不会转换成知识 Chunk。

### 7. 使用结构化的 300–400 Token 切片和双语词法分析器

Chunk 目标为 300–400 个 E5 Token，重叠约 50 Token；标题和位置上下文也计入模型 512 Token 上限。切片优先尊重标题、段落、页面、幻灯片、工作表和行边界，只有必要时才退化为确定性 Token 窗口。Embedding 文本使用 E5 passage 前缀，查询使用 E5 query 前缀。

原始 Chunk 用于引用，另生成一份词法字段：中文片段使用固定版本的中文分词库，英文做 Unicode 规范化和大小写折叠，数字和标识符保持原样。查询使用同一分析器。这样可补足 FTS5 默认 Unicode Tokenizer 对中文 BM25 的不足。

词法分析器版本和切片版本写入代次 Manifest，不兼容升级必须触发重建，不能混用表示。

### 8. 使用确定性 Hybrid 检索和经过标定的证据阈值

默认查询分别召回 40 条 BM25 和 40 条 Dense 候选，使用 RRF 融合，按 Chunk Key 去重，对前 30 条 Query/Passage Pair 本地重排，应用文档多样性规则，最终最多返回六条证据。数量和融合常量均由经过校验的配置控制。

Reranker Manifest 包含在版本化评测集上标定的验收阈值。标定过程在“无答案误命中率不超过 10%”的约束下选择 F1 最高的阈值。运行时拒绝缺少阈值的 Manifest，管理员可以显式覆盖。

`RagEvidence` 包含原文、稳定文档 ID、显示文件名、类型化位置和诊断分数，诊断值不得描述为经过概率校准。`RagSearchResult` 区分有证据、无证据、不可用和已披露的仅词法降级。

工具把证据序列化到“不可信证据”包装中。Agent 上下文明确规定，文档中的指令不能更改系统策略或授权工具。主 LLM 为远程模型时，只把最终证据和引用元数据加入请求。

### 9. 使用固定 ONNX 模型 Manifest，禁止远程代码

为 `intfloat/multilingual-e5-small` 和 `BAAI/bge-reranker-base` 提交 Manifest，固定不可变仓库 revision、产物路径与 SHA-256、Tokenizer 文件、Pooling、归一化、维度、精度、最大序列长度、许可证、标定阈值和 Profile ID 输入。

跨平台基线直接使用 ONNX Runtime 和原生 Tokenizer，不使用 `sentence-transformers + PyTorch`，以减小可选安装体积与内存占用，并统一 Execution Provider 接口。只加载经过审核的 ONNX 文件，`trust_remote_code=False`。

共享模型缓存 Manager 在文件锁下执行“下载到临时路径—哈希校验—原子发布”。自动下载默认开启，同时提供管理员预取命令支持离线部署。模型字节不计入用户配额。

### 10. 通过本机实测选择执行后端，而不是只看硬件名称

`HardwareAwareRuntime` 枚举已安装的 ONNX Execution Provider 和兼容模型变体。自动模式可比较 CPU INT8、Apple CoreML、NVIDIA CUDA FP16、Intel OpenVINO 和 Windows DirectML。Provider 包保持可选，运行时不自动安装驱动或修改 Python 环境。

每个候选都执行预热、固定样例正确性检查和有界基准测试，分别测量：

- 单条查询 Embedding 延迟。
- 入库批量 Embedding 吞吐。
- 20–30 个 Pair 的 Reranker 延迟。

默认总预算 60 秒，每个候选最多 10 秒。Embedding 与参考结果的余弦相似度必须至少为 0.999；Reranker 必须保持固定样例排序一致，归一化分数绝对差不超过 0.001。候选还必须通过内存和稳定性策略。

选择结果按硬件、操作系统、架构、可见设备、Provider 版本、运行时版本和模型 Manifest 缓存。不同工作负载可以选中不同后端。加速器错误会让对应候选在当前指纹下进入黑名单，发送一次事件后依次回退到其他本地 Profile，最终回退到 CPU。

同一模型产物只改变执行设备时，数值兼容校验通过即可复用向量。模型产物、Tokenizer、Pooling、维度、归一化或量化发生变化时，创建新的 Embedding Profile 并在后台重建索引代次。Reranker 可直接切换。

不根据强硬件自动选择 BGE-M3，因为更换 Embedding 模型会隐式改变存储、质量与行为。更大模型以后只能作为经过独立评测的管理员显式 Profile。

### 11. 复用类型化出站事件并增加 RAG 专用事件

在现有出站事件旁新增 `RagProgressEvent`，包含操作 ID、操作类型、阶段、状态、可选 current/total、安全文档元数据、安全错误类别和回退文本，不包含文档文本或证据。

Manager 通过现有出站总线发送事件。WebSocket Adapter 为 WebUI 序列化结构化形式。渠道协调层把它视为进度事件：支持编辑的 Adapter 更新同一消息，纯文本 Adapter 使用最少的开始/结束消息。事件去重与限频以 `(operation_id, phase, state)` 为键。

后台任务持久保存最终通知所需的来源渠道、chat ID 和 Reply/Thread 元数据，但这些字段不提供授权。通知失败只记录安全日志，不改变任务状态。`/rag status` 始终从 Store 读取。

不建设第二套 RAG 事件总线，因为它会重复路由、渠道能力、WebSocket 序列化和失败语义。

### 12. 明确 RAG 配置和可选依赖

新增 Pydantic `RagConfig`，覆盖启用状态、存储、配额和磁盘策略、解析限制、并发、切片、词法分析器、模型 Manifest 与缓存、下载策略、运行模式与基准测试、检索数量、标定阈值、事件限频、重试和保留策略。配置校验拒绝不兼容维度、可变模型引用、无效配额关系或强制但不可用的后端。

Core 包只通过可选导入或 Protocol 引用 RAG 类型。增加 `rag` 可选依赖组，包含 CPU 推理、模型下载、Tokenizer、中文分词、数值数组和 USearch。平台加速依赖按主机单独安装。CI 同时验证“无 RAG Core”和“安装 CPU RAG Extra”两种环境。

### 13. 通过 Fake、存储集成、评测和平台冒烟测试验证

为 Embedder、Reranker、Clock、Event Publisher、Parser Worker、Disk Probe 和 Hardware Probe 提供可注入接口。普通测试使用确定性 Fake，避免 CI 意外下载模型。

存储集成测试覆盖事务、并发配额预占、代次、删除、重启恢复、损坏和用户隔离。解析 Fixture 覆盖每种格式及不安全、空内容场景。工具和渠道测试证明主体不能被覆盖，群聊失败即关闭。WebUI 测试覆盖事件投影与重连。

版本化双语评测集计算 `private-rag-retrieval/spec.md` 中的规范阈值，并生成 Manifest 验收阈值。可选真实模型 Job 在三个操作系统上覆盖 CPU，并在发布硬件可用时覆盖加速器。

## 风险与权衡

- **[派生索引可能超过原始文件配额]** → 设置全局存储上限和剩余磁盘保护，量化向量，展示索引大小，并在磁盘耗尽前拒绝。
- **[每主体 HNSW 代次让小更新成本更高]** → 后台构建并保持旧代次可用，先保证正确性，再评估增量构建优化。
- **[CPU 处理接近 1 GiB 可能耗时数小时]** → 持久化异步任务、批量推理、查询优先和持续进度反馈，不承诺统一完成时长。
- **[中文分词增加一个版本化表示]** → 固定分析器版本并写入 Manifest，升级时显式重建。
- **[硬件后端可能已安装但更慢或数值不兼容]** → 按工作负载实测并设置正确性门禁，最终回退 CPU。
- **[CoreML 编译或加速器预热可能拖慢首次使用]** → 在支持时缓存编译结果，并在有界基准测试期间发送准备事件。
- **[文档 Prompt Injection 可能影响远程主 LLM]** → 把证据视为不可信数据、减少传入证据，并阻止证据控制身份或工具授权。
- **[不同渠道的身份元数据不一致]** → 增加明确能力契约，Adapter 通过契约测试前失败即关闭。
- **[SQLite 与 HNSW 可能在中断后不一致]** → 使用不可变版本文件、事务 Manifest、校验、启动协调和重建路径。
- **[某些 Python/平台组合缺少原生 Wheel]** → 保持 RAG 可选，清晰验证安装，维护 CPU 支持矩阵，不影响非 RAG 安装。

## 迁移方案

1. 先增加可选配置、Protocol、类型和禁用状态行为，不注册用户可见 RAG 命令。
2. 增加带明确 Schema 版本的新存储根；不迁移现有 Session 文件。
3. 增加 CPU 模型预取和验证，再在 `rag.enabled` 后启用入库与检索。
4. 实现渠道私聊能力，只为通过身份与隐私契约测试的 Adapter 暴露命令。
5. 增加 WebUI 和渠道进度展示。
6. 各平台加速 Profile 通过冒烟测试后逐个启用。
7. 发布评测结果后，才把该 Profile 视为发布就绪。

回滚时停止注册 RAG 命令和工具，并停止接受新任务，但保留 Store。重新启用后从安全状态恢复。如果必须回滚索引 Schema，兼容时继续使用旧的不可变代次和 Manifest；不兼容时保留原始文件并重建，不执行不安全降级。
